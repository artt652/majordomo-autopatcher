AutoPatcher applies your changes to system files and brings them back, together with the modules you need, after every MajorDoMo update.

Warning: this tool can break the system.

A patch changes MajorDoMo system files and is applied automatically on every start. The php -l check catches syntax errors only. It does not find logic errors or incompatibility with the current system version or other patches. A wrong patch can stop the cycles or make the control panel unavailable, and it is applied again on the next start.

Add only patches you are sure about, and check the system after every apply.

If the panel is unavailable, recover from the console:

  1. move the patch file out of cms/autopatcher/patches/ to any other folder, so it is not applied on the next start;
  2. restore the originals from cms/autopatcher/backup/<date>_<patch>/: every file is stored there under its own path with the .bak extension;
  3. restart the system.

1. How it works

On every start cycle.php removes the module install markers, and control_modules calls install() of every module. This happens before the cycle_*.php threads are launched. AutoPatcher does its work at that moment:

  1. checks all enabled patches and applies the pending ones;
  2. installs modules from its list if they are missing or an update overwrote their files;
  3. if a module was installed, checks the patches once more.

Cycles start with the patched files, so no restart is needed at system start. At start the module does not use the network (except downloading a missing archive with short timeouts). Module updates are checked in the background on the HOURLY event.

The way the system is updated does not matter: System update, git pull, Market «Update all» or a manual copy. The patcher compares file contents, not version numbers.

2. Quick start

  1. Press Add patch.
  2. Paste a GitHub PR or commit link, or the patch text, or upload a .diff file. The file name may be left empty.
  3. Press Submit. The patch card opens with the state of every file.
  4. If the state is «pending», press Apply or wait for the next system start.

For a module that must stay installed: Add module, paste the GitHub repository link and save. The module name is detected from the archive.

3. Patch formats

Patches are applied in ascending order of the number at the start of the file name: 5-…, 10-…, 100-…. Change the order with the up / down arrows in the list or the «Order» field in the patch card. The file is renamed automatically, and the state, enabled flag and remembered checksums stay with the patch; a file renamed manually on disk is treated as a new patch. Order matters only when patches change the same lines: a base patch must come before one built on top of it. Keep one patch per change: they are easier to refresh and revert separately.

Unified diff — *.diff, *.patch

Regular git diff or diff -u output, paths from the MajorDoMo root. For example, a change of your fork against upstream:

cd /path/to/htdocs
git diff upstream/alpha -- lib/hooks.inc.php > cms/autopatcher/patches/10-hooks-php8.diff

New files can be created (--- /dev/null). Deletion, rename and binary files are not supported: such files must be excluded with an # exclude: line.

SEARCH/REPLACE — *.replace

Only a unique fragment is searched, so such a patch survives changes in neighbouring lines:

# title: PHP 8: implode() with NULL
FILE: modules/scripts/scripts_edit.inc.php
<<<<<<< SEARCH
exact lines as they are in the file now
=======
lines after the fix
>>>>>>> REPLACE

One file may contain several FILE: and SEARCH/REPLACE blocks. The fragment must occur in the file exactly once and start at the beginning of a line.

Header lines

LinePurpose
# title: …patch name in the list
# description: …notes, may be repeated
# source: URLwhere the patch comes from; enables «Refresh from source»
# root: folderprepended to all paths when diff paths are not relative to the MajorDoMo root (e.g. modules/tinyfm)
# exclude: path or maskskip a file (docs/*, .github); path as in the diff, without # root:

In a diff, header lines must come before the first diff --git / ---.

4. Patch from a GitHub PR or commit

LinkWhat is downloaded
github.com/O/R/pull/Nall changes of the PR
github.com/O/R/commit/SHA, …/pull/N/commits/SHAone commit
github.com/O/R/compare/A...Bdifference between branches
any .diff / .patch linkas is
  1. In «Add patch» paste the link, leave the text empty, press Submit.
  2. The diff opens in the editor. The title comes from the PR or commit; files missing in this installation, service folders and unsupported changes are excluded with # exclude: lines. The excluded list is shown above the form.
  3. Review the text and press Submit again: the patch is saved.

If the PR is already merged (PR: merged), after a system update the patch becomes «applied» by itself and can be disabled.

Refresh from source in the patch card downloads the diff again: the PR may have new commits. Your # exclude: and # description: lines are kept. If the patch is applied and the diff changed, revert it first.

5. Patch states and what to do on a conflict

StateMeaningWhat to do
appliedthe new text is already in the files: applied earlier or the fix is upstreamnothing
pendingthe old text is found exactly once, the patch can be appliedApply, or wait for the system start
conflictthe code was changed by an update: neither old nor new text found. Files are untouched. One entry appears in System errorsopen the patch card to see which file and fragment did not match; update the patch for the new code, or disable it if the fix is upstream
errore.g. php -l found a syntax error in the result, or the patch has an unsupported changefix the patch text according to the message

Guarantees: a patch is applied to all its files at once or not at all. A new file is first written to a temporary one, checked with php -l and only then replaces the original. The original is backed up first. A conflict never writes anything.

The table state is checked against the files every time the module page is opened.

6. Reverting a patch

«Revert» applies the patch backwards and disables it, otherwise automatic mode would apply it again on the next start. To bring it back, enable it and press Apply.

Before reverting, the patcher checks whether other applied patches change the same lines (one patch is built on top of another, or a patch is a cumulative git diff of a whole file). Then the revert stops and lists those patches. After confirmation they are all reverted together: the patcher picks an order that leaves no fragments behind, and disables them. If no such order exists, files are not changed.

«Delete» first reverts an applied patch, then moves the patch file to cms/autopatcher/deleted/. To avoid cutting native code, the patcher reverts without asking only when the files are exactly as it left them after applying: it remembers their checksums after every apply. If the files changed since (a system update, a module installation, or the patch was applied before version 1.2.2), e.g. the fix is already upstream, it asks: «Revert and delete» or «Delete without reverting». If reverting fails (conflict), the patch is not deleted.

7. Modules: automatic installation and updates

Adding

  • Link: GitHub repository (github.com/O/R), branch (…/tree/branch), archive (…/archive/…tar.gz) or any .tar.gz. If empty, the link is taken from Market.
  • Or a file: a .tar.gz archive.
  • Name and title may be left empty: they are taken from the archive (modules/<name>/<name>.class.php). The record is saved right away and the archive is downloaded in the background; until then the record has a temporary name from the link.
  • Installed marker: a file whose absence means the module must be installed. Default modules/<name>/<name>.class.php. It must be in the archive, otherwise the module gets the «marker not found» status.

When to install

  • Only when the module is missing: the marker file does not exist.
  • Reinstall when an update changed its files: after every installation checksums of the module files are saved; if any of them is changed or deleted at start, the module is installed again. For modules that overwrite core files.

Installation uses the same path as Market, from the local archive copy in cms/autopatcher/packages/. Without a copy the archive is downloaded: at system start with short timeouts (5 s to connect, a stalled download is aborted after 10 s); MajorDoMo Connect archives only with the Download button.

Updates

LinkCompared by
GitHub: repository, branch, branch archiveSHA of the latest commit
GitHub: tag archive (…/archive/refs/tags/…)tag of the latest release
other serversETag or Last-Modified

Modes: «Do not check», «Check and notify» (the module row shows «Update available» and an Update button), «Check and install automatically». Checks run on the HOURLY event at the interval from settings and with the «Check for updates» button.

Log

«Install log» of every module shows the steps of the last installation and the list of files. It is written after every step, so after a failure you can see where it stopped. If a module installer killed the process at start, the module gets the «install crashed» status and is installed manually only.

8. Settings

  • Apply patches automatically: at system start. When off, patches are only checked.
  • Install modules automatically: the same for modules.
  • Restart services after PHP files were changed: after manual apply, revert or install, so cycles pick up the new code. Not needed at system start.
  • Check module updates every, h: background check interval.

Apply all now does the same as at start without waiting for a restart.

9. Command line

php /path/to/htdocs/modules/autopatcher/cli.php status   # changes nothing
php /path/to/htdocs/modules/autopatcher/cli.php apply

Exit code 1 means there are conflicts or errors. Useful in start scripts. Called over HTTP, cli.php returns 403.

10. Where the data is

Everything is in cms/autopatcher/. Neither a system update nor an update of this module touches this folder.

patches/your patches
packages/module archives <name>.tgz, install logs, checksums
backup/originals of changed files (*.bak), last 30 runs
deleted/patches removed from the list

config.php and the cms/autopatcher/ folder are never patched. After uninstalling the module, changed files stay as they are; to restore the originals, revert the patches before uninstalling.

If a whole module is modified, the standard ignore_updates table can be used instead: the system update skips modules/<name> and templates/<name>. AutoPatcher is for targeted changes, including lib/ and root files.

11. Troubleshooting

  • «Last run» on the main page shows when and how the last run went (boot means system start). If a run was interrupted, it shows at which stage.
  • Log: cms/debmes/<date>/autopatcher.log.
  • State without a browser: cli.php status.
  • If «Last run» does not change after a restart, check that cycle.php contains the module reinstall block: grep -n "Re-installing module" cycle.php.
  • If a module is reinstalled on every start, its marker file does not appear after installation, or the module changes its own files. Fix the «Installed marker» or choose «Only when the module is missing».
